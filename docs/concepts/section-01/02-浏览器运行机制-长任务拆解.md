# 长任务 与 主线程阻塞
- 正常情况下，浏览器每16ms渲染一帧

## 长任务
- 主线程上连续执行超过50ms的任务
- 人类对 100ms 内的响应感觉是「即时」的；留 50ms 给渲染和输入处理，任务本身最多占 50ms

## 长任务拆解
### 核心原理
- 把一个连续运行的200ms的大任务，拆分成4个50ms的小任务，把每个小任务之间的控制权还给浏览器，让浏览器有机会渲染

```plaintext
❌ 不拆分：
[========== 200ms 长任务 ==========] → 阻塞 12 帧，UI 完全卡死

✅ 拆分后：
[=50ms=] 让出 [=50ms=] 让出 [=50ms=] 让出 [=50ms=]
         ↑        ↑        ↑        ↑
    中间可以渲染一帧、响应输入、执行其他任务

```

### 拆分的两个关键行为
- 切片（Chunk）: 把大循环 / 大计算按数量或时间分成小片      （相当于把一大块肉分成小块炒）
- 让出（Yield）: 每片执行完后，主动把控制权还给浏览器       （炒完让锅歇一下，让服务员能上菜）

#### 四种让出主线程的方法

| 手段                  | 写法                                             | 让出精度                      | 优先级               | 浏览器兼容              |
| --------------------- | ------------------------------------------------ | ----------------------------- | -------------------- | ----------------------- |
| setTimeout(0)         | await new Promise(r => setTimeout(r, 0))         | 差（≥4ms 延迟，排宏任务末尾） | 最低                 | 全部                    |
| requestAnimationFrame | await new Promise(r => requestAnimationFrame(r)) | 中（下一帧前执行）            | 渲染前               | 全部                    |
| scheduler.yield()     | await scheduler.yield()                          | 好（立即让出，保留继续位置）  | 较高（continuation） | Chrome 115+             |
| requestIdleCallback   | await new Promise(r => requestIdleCallback(r))   | 低（浏览器空闲时才执行）      | 最低                 | Chrome 47+（无 Safari） |

#### 方法1: setTimeout (0) - 兜底用
- 优点： 兼容性最好， 所有的浏览器都支持； 写法简单。
- 缺点： 有最小 4ms 的延迟； 排到宏任务队列末尾，可能被其他宏任务插队； 让出后恢复执行的优先级最低

```js
const process = async () => {
    for (let i = 0; i < 1000000; i++) {
        doWork(i);
        if (i % 5000 === 0) {
            await new Promise(r => setTimeout(r, 0));
        }
    }
}
```

#### 方法2: requestAnimationFrame 
- 优点： 和浏览器渲染节奏同步，适合动画场景； 在让出后下一帧前恢复，时机可控。
- 缺点： 标签页不可见时，rAF会暂停，任务可能会卡住； 不是所有任务都需要等待下一帧。

```js
const process = async () => {
    for (let i = 0; i < 1000000; i++) {
        doWork(i);
        if (i % 5000 === 0) {
            await new Promise(r => requestAnimationFrame(r));
        }
    }
}
```

#### 方法3: scheduler.yield() - 首选
- 优点： 立即让出，无额外延迟； 恢复执行时优先级较高(continuation); 不会被排到宏任务末尾
- 缺点： Chrome 115+ 才支持， 需要polyfill; API 比较新

```js
const process = async () => {
    for (let i = 0; i < 1000000; i++) {
        doWork(i);
        if (i % 5000 === 0) {
            await scheduler.yield();
        }
    }
}
```

#### 方法4: requestIdleCallback - 后台任务专用
- 优点： 只有在浏览器空闲时执行，完全不影响交互； 适合非紧急后台任务（预加载，索引构建）
- 缺点： 1. 不可预测，可能很久才执行； 2.Safari不支持； 3.不适合用户正在等待结果的任务
  
```js
const process = async () => {
    for (let i = 0; i < 1000000; i++) {
        doWork(i);
        if (i % 5000 === 0) {
            await new Promise(r => requestIdleCallback(r));
        }
    }
}
```

- requestIdleCallback 的 deadline 参数：
```js
const work = (deadline) => {
    while (deadline.timeRemaining() > 0 && tasks.length > 0) {
        doTask(tasks.shift());
    }

    if (tasks.length > 0) {
        requestIdleCallback(work);
    }
}

requestIdleCallback(work);
```

### 可中断设计： AbortController
- 场景举例： 用户发了一条消息，推理跑了一半，用户又发了一条新消息，此时旧推理应该立即停止，而不是继续跑完浪费时间

```js
// 可中断的分片处理 - 使用
const controller = new AbortController();

// 开始处理
processInChunks(bigArray, 5000, item => compute(item), controller.signal);

//. 点击取消
document.getElementById('cancel').onclick = () => {
    controller.abort();
}
```

#### 中断检查的频率
| 检查频率                  | 响应速度                                        | 性能开销                      | 
| --------------------- | ------------------------------------------------ | ----------------------------- | 
| 每条数据都检查         | 最快（<1ms 内响应）        | 开销大（频繁读属性） |
| 每片检查一次 | 较快（一片的时间，如 10~50ms） | 开销小（推荐）           |
| 每个阶段检查     | 慢（可能几百 ms 才响应）                         | 开销最小）   |


### Web Worker

#### 数据传递 - 两种方式
```js
// 结构化克隆 - 数据被复制一份
worker.postMessage({ bigArray: new Float32Array(1_000_000) });

// Transferable - 所有权转移，零拷贝
const buffer = new ArrayBuffer(1024 * 1024 * 50); // 50MB
worker.postMessage(buffer, [buffer]); // 第二个 buffer 变成要转移的对象
// 执行后；主线程的buffer 变为 detached
```

- 可转移的类型： ArrayBuffer、MessagePort、ImageBitmap、OffscreenCanvas、ReadableStream、WritableStream、TransformStream
